# v1.7.0 —— exec 审批只剩一个写入者

无新功能、无界面变化。修的是一处**界面承诺与脚本实际行为对不上**的地方。

## 原来是两个写入者，意图相反

界面上的「最高权限」开关要输 sudo 口令才能打开，看起来是一道门。后端也确实照这个
开关办事——`setImmediate` 里读开关状态，开着就放宽 `exec-approvals.json`，
关着就把 `ask` / `security` / `agents` 三个键 **删掉**，恢复引擎默认。那条路径是对的。

问题在 `backend/patch-config.js`。它每次部署都**无条件**写：

```js
approvals.defaults.ask = 'off';
approvals.defaults.security = 'full';
approvals.agents = { '*': { allowlist: [{ pattern: '*' }] } };
```

于是同一个文件上有两个写入者，朝相反方向写。而 `deploy-release.sh` 的顺序让这件事
变得具体：

```
patch-config（写成全开）
  → restart-openclaw-runtime（**网关带着全开的审批重启**）
    → service-restart（后端启动，按开关收敛回去）
```

**文件最终看起来是安全的，但网关是在全开的那一刻被重启的。** 文件与运行中的状态
是否一致，取决于引擎缓不缓存这份审批——那不是我们能控制的，也不该去赌。

还有一条更直白的：后端若启动失败（依赖装坏、端口占用、ABI 不匹配），收敛那一步
根本不会跑，全开状态就那样留着了。

## 这一版做了什么

`patch-config.js` **不再触碰 exec 审批**。判据只实现一次，就在后端那条跟随开关的
路径上。这跟 `openclaw-config.ts` 把配置读写收进一个入口、
`snapshot-openclaw-config.sh` 一份实现两处调用，是同一条原则。

不写反而在两个方向上都更对：文件里保留的是**上一次后端收敛后的状态**——

- 开着最高权限的用户：网关重启时读到的仍是放宽的
- 关着的用户：读到的是收紧的

不再有任何一次「先写反、再改回」。首次安装时文件尚无状态，由后端首次启动时收敛。

`commands.bash` 那段保留——它是引擎 2026.3.12+ 要求的，与审批无关。

## 明确不做的

这一版**不动访问控制**：登录仍是选配、监听仍是 `0.0.0.0`。那是产品取舍
（自托管单人主机上强制口令可能只是挡路），由仓库所有者决定，不由这次修复顺手改掉。

需要提醒的是：默认部署的防护要靠部署者自己补。作为参照，本项目自己的公网实例是
三层——ufw 只放行 443/22（后端端口公网不可达）、nginx Basic Auth、以及 ClawOPT
自身的登录（口令 scrypt 哈希 + `allowedHosts` 白名单）。

## 守卫

先在旧代码上跑红（3 条），再改实现：

- 用户自己收紧过的审批不被放宽
- 不往里塞通配 allowlist
- 审批文件**逐字节不变**——连重新格式化都不该发生
- 审批文件不存在时也不去创建它（这条在旧代码上本来就绿，保留作为边界记录）
