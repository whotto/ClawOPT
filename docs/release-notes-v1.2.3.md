# v1.2.3 —— 配置访问加固

这一版只做一件事：**把读写 `~/.openclaw` 配置这条线收进一个受控入口**。
没有新功能，没有界面变化。绝大多数用户升级后不会感觉到任何区别——
除非他们正好踩中下面这几件事之一。

## 修的是什么

以下缺陷在 **v1.2.2 及更早版本上全部存在**，不是本版引入的。
它们由连续五轮对抗测试挖出来，每一条都有可复现的步骤。

### 一、后端可以被一个命名管道永久挂死（匿名可达）

`~/.openclaw` 下的配置文件如果不是普通文件（命名管道、目录、字符设备），
同步的 `readFileSync` 会**永久阻塞**：端口还在 LISTEN、日志一声不吭、
所有路由再也不响应，只能 `kill -9`。

实测有四条不同的入口能触发，其中两条只需要一次匿名请求
（默认安装不开登录）：一次 `GET /api/models`、一次 `POST /api/config/max-permissions`、
发一条群消息、或者建一个 Agent。

现在所有配置读取都先确认目标是普通文件，不是就立即失败并说明原因。

### 二、配置解析报错会把凭据带进 HTTP 响应体

V8 的 JSON 报错有一类会把输入原文嵌进错误消息：

```
JSON.parse('{"apiKey":"sk-LEAK","x":undefined}')
  → Unexpected token 'u', ..."sk-LEAK","x":undefined}" is not valid JSON
```

而 `openclaw.json` 里存着 `gateway.auth.token`、`gateway.auth.password`
和每一家模型的 apiKey。这些消息此前被原样塞进 500 响应。
`fs` 的报错同理会带出主机绝对路径与用户名。

现在错误细节只保留错误码或「类别 + 位置」，不含任何原文与路径。

### 三、写配置时会先把它截断成 0 字节

`fs.writeFileSync` 先截断再写。跨进程实测：7 次写入过程中，
一个并发读者**三次**观察到 `openclaw.json` 长度为 0。

这是那台机器上**唯一一份** OpenClaw 配置——gateway 凭据、所有模型 apiKey、
全部 Agent 定义都在里面，而 ClawOPT 从没为它做过备份。
进程在那个窗口里被杀（OOM、`systemctl restart`、断电、
或 `Restart=always` 拿着坏产物反复崩溃），配置就永久没了。

现在改为「同目录临时文件 → fsync → rename」。`rename(2)` 在同一文件系统内是原子的：
读者要么看到旧的完整内容，要么看到新的完整内容，没有第三种状态。

**软链会被穿透**：如果你把 `openclaw.json` 软链到别处（多机共享、放同步盘里），
以前的写入会把软链换成普通文件、静默拆掉那个安排；现在写的是它指向的真实文件。

### 四、配置读不动时，装配「成功」但什么都没写

`openclaw.json` 解析失败时，读取函数返回 `null`，而上游把它当成
「配置没有变化」——于是建 Agent 的接口返回 `success: true`，
配置文件一个字节没变，Agent 从未被注册，界面上却不会报错。
用户过后用同一个 ID 重试，还会被「该 ID 已存在」挡住。

同一类问题还有几种更隐蔽的形状：`JSON.parse` 对 `null`、`false`、`0`、`[]`
**全都成功返回**；而 `{"agents": []}` 会让写入挂到一个数组的具名属性上，
`JSON.stringify` 序列化数组时把它直接丢弃——同样是「报成功、没写入」。

现在这些都会明确失败，并区分出四种可分辨的原因
（读不动 / 解析失败 / 带注释的 JSON5 / 形状不可用）。

### 五、删除报成功而一个字节没删

`DELETE /api/sessions/:id` 在配置读不动时返回 200，
而配置条目、工作区、agent 状态目录、记忆库全部还在。现在如实报错。

## 升级注意

- **无需改配置，无迁移步骤。**
- 少数此前被静默吞掉的失败现在会显式报错。如果你的 `openclaw.json`
  带有 JSON5 注释，或者内容有问题，升级后会**明确告诉你**而不是装作正常——
  这是有意的：一个显示了却不生效的开关，比没有这个开关更糟。
- 群消息、会话列表、模型列表这些只读界面在配置损坏时**不会**整体报错，
  会降级显示并在服务端日志里说明原因。

## 已知限制

- 只读接口的响应里新增了一个 `configReadFailed` 标记，用来区分
  「配置读不动」与「本来就没配」。**本版还没有界面消费它**——
  用户看到的仍是一个空列表，区别只体现在服务端日志里。
  界面上的区分安排在下一版。这里写出来，是因为一个存在却没人读的字段
  不该被当成已经生效的能力。
- 本版有一道机械闸门盯着新增的文件读写（`backend/test/fs-call-sites.test.ts`）。
  它是一张词表加一条按行正则，**可以被绕过**——字符串拼接、`eval`、
  经由某个库间接读文件都在它视野之外。它只保证「用已知写法新增的文件操作会被人看见一次」，
  **不是**「配置读写只有一个入口」的证明。真正的保证来自运行时闸门。
- 基线里还有 57 处文件读写没有逐个审计过。它们大多读写工作区文件、上传件、
  预设包，与 `~/.openclaw` 下的配置无关。这个数字只降不升。
