# 本套技能的编写规格（House Spec v1.0）

> 依据：agentskills.io 开放规范 + 四家平台对标（见 `BENCHMARK.md`）。
> **所有 14 个技能必须满足本规格。新增技能同样适用。**

## 0. 硬性合规（不满足就是不合格）

- 目录名 = frontmatter 的 `name`，1-64 字符，仅小写字母/数字/连字符，不以连字符开头结尾，无连续连字符
- `SKILL.md` **≤500 行**，正文建议 **<5000 tokens**；超了把明细下沉到 `references/`
- 文件引用只保留**一层深度**，不做深层嵌套链
- 目录约定：`SKILL.md` + `references/`（按需读的文档）+ `assets/`（模板）+ `scripts/`（可执行）

## 1. Frontmatter 模板（六字段全填，不留空）

```yaml
---
name: skill-name
description: 一句说清「做什么」+「什么时候用」+「什么时候不用」，并塞进真实触发语。这是路由依据，写含糊技能就不会被触发。≤1024 字符。
license: Proprietary. 内部使用。
compatibility: 面向 OpenClaw 工作区技能；需要联网检索能力（web_search / web_fetch）。
metadata:
  author: OPT-Team
  version: "1.0"
  role: intel-research
  updated: "2026-08-22"
allowed-tools: Read Grep Glob web_search web_fetch memory_search memory_get
---
```

**`allowed-tools` 是最小权限声明**：只写这个技能真正需要的。诊断类技能绝不写 `Write` 到别人的工作区；调研类技能绝不需要 `exec`。

## 2. 正文必备的九个段（顺序固定）

```markdown
# 技能中文名 · skill-name

> 一句话定位

## 硬约束            ← 读到就生效的红线，3-6 条，动词开头
## 权限与数据边界      ← 读什么/写什么/发不发外部/敏感数据怎么处理  ★对标 360+WorkMate
## 何时使用 / 何时不用  ← 正反例表 + 升级降级信号（转给哪个角色）
## 输入输出契约        ← 吃什么、吐什么、能被哪个技能接      ★对标 Coze 子工作流
## 流程               ← 每步：目标 / 动作 / 标准话术 / **退出条件** / 常见失败
## 自检闸门           ← 交付前逐条打勾，有一条不过就回退到第几步   ★对标 Coze 试运行
## 量化验收指标        ← 可数的门槛，不是"做得好/不及格"        ★对标 WorkMate
## 常见失败模式        ← 表格：失败 / 表现 / 怎么避免           ★四家都没有
## 降级与失败路径      ← 搜不到 / 收敛不了 / 时间不够 怎么办
## 执行留痕与记忆写回   ← 留什么痕、可回溯什么、写进哪个文件     ★对标 WorkMate 审计 + 智谱 Memory
```

## 3. 退出条件（Exit Criteria）的写法

这是本规格的核心。每一步都要能被二值判定：

| ❌ 不合格 | ✅ 合格 |
|----------|--------|
| 用户理解了 | 用户复述了调研目标，或明确说"你看着办" |
| 分析得差不多了 | 成本和收益各追问过两轮"还有吗"，且用户说不出新条目 |
| 信息够了 | P0 信息点覆盖率 ≥70%，未覆盖项已进缺口清单 |

并且必须显式写死这句：

> **未满足本步退出条件，不得进入下一步。**

对话型技能（JTBD、ROI）还要加：

> **每轮输出 3-5 句话以内。抛出问题后必须等用户回应。禁止合并输出多步内容。**

## 4. 输入输出契约的写法

```markdown
## 输入输出契约

**输入**：用户的一句话需求 + （可选）已有的 XX 结论
**输出**：`assets/xxx.md` 格式的一页纸，含字段 A/B/C
**上游**（谁的输出能喂给我）：`quick-research` 的数据点 / `point-intel` 的核实结论
**下游**（我的输出能喂给谁）：`five-steps-quick` 的需求栏 / 科学决策的 `roi-deep-dive`
**串联示例**：`quick-research` → `jtbd-demand` → `five-steps-quick`
```

## 5. 量化验收指标的写法

不写形容词，写数字：

| ❌ | ✅ |
|----|----|
| 搜索要充分 | 关键词 ≥3 组、来源类型 ≥3 类、必含 1 轮反面证据 |
| 交互节奏要好 | 5-7 轮；每轮 ≤5 句；每步等待用户回应 |
| 报告要完整 | 四要素（问题/根因/解法/预期效果）缺一不可；每条信息 3 标签齐全 |
| 结论要客观 | 全文 0 处出现「建议/应该/值得做/综合来看」 |

## 6. 权限与数据边界的写法

```markdown
## 权限与数据边界

| 项 | 边界 |
|----|------|
| 读 | 本工作区 `memory/`；联网公开信息 |
| 写 | 仅本工作区 `memory/`；**不写入任何其他 Agent 的工作区** |
| 外发 | 无。本技能不产生任何对外发送动作 |
| 敏感数据 | 不把搭档的私人信息、内部数据带入搜索查询串 |
| 升权 | 不需要 `exec`、不需要 sudo、不安装任何包 |
```

**为什么必须写**：360 报告近四成 Skill"带病上岗"，风险入口就是技能。技能自带权限声明，等于给审计一个可比对的基线——平台强制是外部约束，声明是内部自证，两者互补。
