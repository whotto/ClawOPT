# 技能锻造 · skill-authoring

> `EVOLUTION.md` 规定了技能该怎么沉淀、审批、淘汰，但没规定技能该怎么写。
> 这一条补上那个缺口，并且守住同一道门：**新技能先进 `_pending/`，不进 `skills/`。**

## 硬约束

1. **一切产出先落 `skills/_pending/<name>/`。** 未经搭档明确批准，不得写入 `skills/` 生效目录，不得改动任何已生效技能的 `SKILL.md`。
2. **不给自己写权限。** 本技能不修改 `SOUL.md`、`USER.md`、`AGENTS.md` 的安全段与红线段。要改路由表，写成 diff 交给搭档。
3. **抽取来源必须是真实执行过的动作**，不是设想的流程。说不出"哪三次任务用过它"，就不该做成技能。
4. **交付前必须跑两个脚本**：`_shared/validate-skills.sh`（十项 House Spec）和 `audit-routing.sh`（路由对账）。任一不过不得交付。
5. **description 是路由依据，不是简介。** 必须同时写清做什么、什么时候用、**什么时候不用**，并塞进搭档真实说过的话。

## 权限与数据边界

| 项 | 边界 |
|----|------|
| 读 | 本工作区全部；`_shared/SKILL-SPEC.md`、`EVOLUTION.md`、`SECURITY.md` |
| 写 | **仅 `skills/_pending/`、`skills/_archived/`、`skills/_rejected/` 与本工作区 `memory/`**；生效目录只读 |
| 外发 | 无。不上传技能到任何技能市场，不联网发布 |
| 敏感数据 | 技能正文不得内嵌任何凭据、token、私人信息、客户名；示例一律用占位符 |
| 升权 | 仅执行本包自带的两个校验脚本；不装包、不 sudo |

## 何时使用 / 何时不用

| 场景 | 用不用 |
|------|--------|
| 同一套动作做过三次以上，想固化 | ✅ 用 |
| 某技能老是不被触发 | ✅ 用（改 description） |
| 技能被触发了却没照着执行 | ✅ 用（补退出条件） |
| 三个月没用过的技能要不要留 | ✅ 用（走淘汰评分） |
| 装一个 360 SkillHub 上的技能 | ❌ → `reference/SECURITY.md` §三 准入六步 |
| 这次任务本身怎么做 | ❌ → 对应的业务技能 |

**升级信号**：抽取到一半发现这不是一个技能而是三个 → 停下来拆，宁可三条窄技能，不要一条什么都干的。

## 输入输出契约

**输入**：一段已执行过的工作流（对话记录 / `memory/` 里的留痕）或一个待改进技能的路径
**输出**：`skills/_pending/<name>/SKILL.md`（+ 可选 `references/` `assets/` `scripts/`）+ 一份《转正申请》含三次真实用例、校验结果、建议路由行
**上游**：`memory/` 的执行留痕；`EVOLUTION.md` 的沉淀阈值判定
**下游**：搭档审批 → 移入 `skills/` → 在 `AGENTS.md` 的 Skill 映射表加一行
**串联示例**：任务执行 ×3 → `skill-authoring`（抽取）→ 搭档批准 → 生效 → 三个月后 `skill-authoring`（评分淘汰）

## 流程

### Step 1 · 判定值不值得做成技能

三个条件同时成立才继续：**做过 ≥3 次**、**下次还会做**、**每次做法基本一致**。

写下这三次分别是什么时候、任务是什么、留痕在哪。

**退出条件**：三次用例逐条写出且能在 `memory/` 里找到对应记录。凑不出三次就转「降级与失败路径」。**未满足本步退出条件，不得进入下一步。**
**常见失败**：把一次性任务做成技能，技能库越来越大，路由越来越糊。

### Step 2 · 定边界与命名

先写"什么时候不用"，再写"什么时候用"。反着写能逼出边界。

命名规则：目录名 = frontmatter 的 `name`，1-64 字符，只用小写字母、数字、连字符，不以连字符开头结尾，无连续连字符。**动词短语优先**（`point-intel` 好过 `intel-tool`）。

**退出条件**：能一句话说清它和现有每一条技能的分界，且不与现有技能重名。
**常见失败**：新技能的触发语和老技能重叠，两条都不会被稳定触发。

### Step 3 · 写 SKILL.md

按 `_shared/SKILL-SPEC.md` 的六字段 frontmatter + 十个必备段落写。骨架直接用 `assets/skill-template.md`。

**写 description 的三件事**：

| 要素 | 反例 | 正例 |
|------|------|------|
| 做什么 | "帮助进行调研" | "把一个说不清的复杂问题做成系统调研" |
| 什么时候用 | "需要时使用" | 塞进真实触发语："这个行业怎么样""赛道值不值得做" |
| 什么时候不用 | 不写 | "单个明确数据点走 `point-intel`" |

**退出条件**：十个段落齐全，`description` ≤1024 字符且含反向边界，正文 ≤500 行。
**常见失败**：description 写成简介。技能不被触发，九成是这里的问题。

### Step 4 · 写退出条件（本步是核心）

每一步都要能被二值判定，并显式写死那句"未满足本步退出条件，不得进入下一步"。

| ❌ 不合格 | ✅ 合格 |
|----------|--------|
| 分析得差不多了 | 成本和收益各追问过两轮"还有吗"，且搭档说不出新条目 |
| 信息够了 | P0 信息点覆盖率 ≥70%，未覆盖项已进缺口清单 |
| 材料准备好了 | 五件材料逐条列出且每件有来路 |

**退出条件**：每个流程步骤都有一条可二值判定的退出条件，且量化验收指标全是数字不是形容词。
**常见失败**：写了流程没写退出条件 —— 这就是"读了技能没执行技能"的根源。

### Step 5 · 校验与转正申请

```bash
bash _shared/validate-skills.sh      # 十项 House Spec
bash audit-routing.sh                # 路由对账，确认不是孤儿技能
```

然后交一份《转正申请》：三次真实用例 / 两个脚本的输出 / 建议加进 `AGENTS.md` 的那一行路由 / 与哪条现有技能有边界摩擦。

**退出条件**：两个脚本零报错，申请已交给搭档。**技能停在 `_pending/`，等搭档一句明确的"可以"。**

### Step 6 · 淘汰评分（定期或搭档提出时）

对每条已生效技能打三项分（各 0-2 分）：**近三个月被触发次数** / **触发后是否真的照着执行** / **产出是否还符合当前标准**。

| 总分 | 处理 |
|------|------|
| 5-6 | 保留 |
| 3-4 | 改进，回 Step 3 |
| 0-2 | 移入 `_archived/`，在 `AGENTS.md` 删掉对应路由行 |

**退出条件**：每条技能都有分数与处理结论，且 `audit-routing.sh` 无孤儿技能告警。

## 自检闸门

交付前逐条打勾，**有一条不过就回退到对应步骤**：

- [ ] 三次真实用例可追溯到 `memory/`　→ 不过回 Step 1
- [ ] 与现有技能的边界写清楚了　→ 不过回 Step 2
- [ ] frontmatter 六字段齐全，name 与目录同名　→ 不过回 Step 3
- [ ] description 含"什么时候不用"　→ 不过回 Step 3
- [ ] 每步都有可二值判定的退出条件　→ 不过回 Step 4
- [ ] 量化验收指标全是数字　→ 不过回 Step 4
- [ ] `validate-skills.sh` 零报错　→ 不过回 Step 3
- [ ] `audit-routing.sh` 无 P0　→ 不过回 Step 5
- [ ] 产物在 `_pending/`，没碰生效目录　→ 不过，立即回滚并向搭档报告

## 量化验收指标

| 指标 | 门槛 |
|------|------|
| 真实用例数 | ≥3 次，且各有 `memory/` 留痕 |
| SKILL.md 行数 | ≤500 |
| description 字符数 | ≤1024，且含 ≥3 条真实触发语 + ≥1 条反向边界 |
| 必备段落 | 10 段，缺 0 |
| 带退出条件的流程步骤占比 | **100%** |
| 量化验收指标里的形容词 | **0** |
| 校验脚本报错数 | **0** |
| 未经批准写入生效目录的次数 | **0** |

## 常见失败模式

| 失败 | 表现 | 怎么避免 |
|------|------|---------|
| 一次性任务做成技能 | 技能库膨胀，路由互相干扰 | Step 1 的三条件是硬门 |
| description 写成简介 | 技能永远不被触发 | 必写触发语 + 反向边界 |
| 有流程没退出条件 | 技能被读了但没被执行 | Step 4 逐步补 |
| 验收写形容词 | "做得好""比较完整" | 全改成可数的数字 |
| 越权自改 | 顺手改了 AGENTS.md 或别的技能 | 只写 `_pending/`，改动以 diff 交付 |
| 技能重叠 | 新旧技能触发语打架 | Step 2 先写边界 |
| 只增不删 | 三年没用的技能还在占路由 | Step 6 定期评分 |

## 降级与失败路径

**凑不出三次用例**：不做技能。写成 `AGENTS.md` 的一条经验沉淀，或 `memory/` 里的一段做法记录，等它真的出现第三次再回来。

**流程还没稳定**：先做成 `assets/` 下的一页纸清单给搭档手动用，用顺了再固化成技能。清单不占路由预算，改起来也没有审批成本。

**校验不通过又找不到原因**：把不合规项如实列出来，标注"未过校验，仅供参考"，**不要为了让脚本过而删段落**。删段落能过校验，但技能会退化成一段说明文。

**搭档没空审批**：技能留在 `_pending/`，在 `MEMORY.md` 记一条待审提醒。**不要因为等不及就自行转正** —— 无沙箱环境下，自由写自己的操作手册等于给一次被污染的会话开了持久化后门。

## 执行留痕与记忆写回

**留痕**：每条技能在 `_pending/` 里附一份《转正申请》，含三次用例、校验输出、建议路由行。转正后申请随技能一起留档，任何人可回溯这条技能是凭什么进来的。

**写回 `memory/YYYY-MM-DD.md`**：

1. 抽取了什么技能、依据哪三次任务
2. 校验命中了哪些不合规项（反复命中的项说明是稳定习惯）
3. 搭档批准 / 打回的原话
4. 淘汰评分的结果与理由

**沉淀进 `MEMORY.md` 的技能记忆 L4 段**：现有技能清单 + 各自的最近触发时间 + 上次评分。**这是淘汰环节的唯一依据** —— 没有这份记录，三个月后没人说得清哪条技能还活着。
