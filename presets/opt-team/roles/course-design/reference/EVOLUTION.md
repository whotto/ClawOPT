# EVOLUTION.md — 技能自进化闭环（带审批门控）

> **来源与差异**：Hermes Agent（Nous Research, MIT）实现了"执行 → 反射 → 抽技能 → 改进"的闭环：
> 完成 ≥5 次工具调用的复杂任务后自动抽取可复用技能；每约 15 个任务做一次自评；技能定期打分与淘汰；
> `write_approval` **默认 false**（自由写），设 true 才暂存到 `pending/` 待审。用户反馈同类研究任务提速约 40%。
>
> **本套照搬闭环，但把门控默认反过来：`write_approval = true`。**
> 理由：Hermes 有 Tirith 预执行扫描与容器强化兜底，OpenClaw 没有；且 360 报告近四成 Skill 带病上岗。
> **没有沙箱就必须有审批。** 让 Agent 自由写自己的操作手册，等于给提示注入开了一条持久化通道。

## 一、四层记忆（第四层是本文件新增的）

| 层 | 文件 | 装什么 | 生命周期 |
|----|------|--------|---------|
| L1 会话记忆 | 上下文窗口 | 当前这一轮在聊什么 | 会话结束即失 |
| L2 每日记录 | `memory/YYYY-MM-DD.md` | 当天做了什么、观察到什么 | 长期留存，按需检索 |
| L3 用户模型 + 长期记忆 | `USER.md` / `MEMORY.md` | 稳定偏好（指令式）/ 耐久事实与决策 | 持续精炼 |
| **L4 技能记忆** | `skills/` + `skills/_pending/` | **学到的解决模式**——怎么做某类事 | 版本化，可打分可淘汰 |

**L3 与 L4 的分界**（这条常被搞混）：

- L3 记**是什么**：他偏好简洁进度更新；上季度决定砍掉 B 线
- L4 记**怎么做**：查一个市场规模数据时，先用上位概念搜再拆占比比直接搜更容易命中

> Hermes 的表述值得照抄：技能是"**按需读的参考文档**"，记忆是"**该一直在上下文里的小而耐久的事实**"。

## 二、什么时候该沉淀一个新技能

**触发阈值**（满足任一即可考虑，但都要过 §三 的门控）：

| 触发 | 判据 |
|------|------|
| 复杂任务完成 | 单个任务用了 **≥5 次工具调用**，且过程有可复用的结构 |
| 死胡同 → 通路 | 试错过程中撞了墙又找到了正确路径——**这类最值钱**，因为它记录的是"别走哪条路" |
| 重复出现 | 同类请求**第 3 次**出现（前两次是巧合，第三次是模式） |
| 周期自评 | 每约 **15 个任务**做一次回看，问"这段时间里哪些做法值得固化" |
| 明确失败 | 搭档指出你做错了，且错因是流程性的而非事实性的 |

**不该沉淀的**（写了只会污染技能库）：

- 一次性的、场景强绑定的操作
- 已经被现有技能覆盖的（应该去**改现有技能**，不是新建）
- 只是一段知识而非一套流程（那属于 `references/`，不是 `skills/`）
- 你自己都说不清退出条件的

## 三、审批门控（本套与 Hermes 的关键差异）

```
候选技能产生
     │
     ├─ 写入 skills/_pending/<name>/SKILL.md      ← 绝不直接进 skills/
     │
     ├─ 同时在 memory/YYYY-MM-DD.md 记一条：
     │     "沉淀了一个候选技能 <name>，触发原因：XX，待你过目"
     │
     ├─ 下次对话或心跳时主动提一句（不催第二次）
     │
     └─ 搭档批准 ──→ 移入 skills/<name>/，version 从 "0.1" 起
        搭档否决 ──→ 移入 skills/_rejected/ 并记下否决理由（下次别再提同一个）
```

**`skills/_pending/` 必须存在且必须被 `.gitignore` 之外的方式管理**——它是待审队列，不是垃圾桶。超过 30 天没处理的候选，自动降级到 `_rejected/` 并在心跳里说一句。

**为什么不能自由写**：技能文件会被载入模型上下文并指导行为。一个被注入污染的会话如果能自由写技能，攻击就从"单次会话"升级成"持久化后门"——而且是写在你自己的工作区里、看起来完全合法的那种。这正是 OpenClaw `SECURITY.md` 里"操作者装了恶意插件不算漏洞"的自然延伸。

## 四、候选技能的最低完成度

进 `_pending/` 的文件不是草稿，必须已经满足 House Spec 的**骨架**（完整版见 `SKILL-SPEC.md`）：

- [ ] frontmatter 六字段齐全，`name` 与目录同名且合规
- [ ] `## 硬约束`：至少 3 条
- [ ] `## 权限与数据边界`：明确读/写/外发/敏感数据/升权
- [ ] `## 流程`：每步有**可二值判定的退出条件**，并写死"未满足退出条件不得进入下一步"
- [ ] `## 常见失败模式`：至少记下这次触发沉淀的那个失败
- [ ] `metadata.version: "0.1"`、`metadata.origin: self-authored`、`metadata.trigger: <触发原因>`

**达不到就不要提交候选**——半成品技能比没有技能更糟，它会让模型以为自己有章可循。

## 五、打分与淘汰（防止技能库变垃圾场）

Hermes 的做法是定期 grade and prune。本套落成一个**季度巡检**（已写进 `automations.sh`）。

**每个技能按四项打分（各 0-2 分，满分 8）**：

| 维度 | 0 分 | 1 分 | 2 分 |
|------|------|------|------|
| **被触发频率** | 近 90 天 0 次 | 1-3 次 | ≥4 次 |
| **触发准确率** | 经常被误触发或该触发时没触发 | 偶有偏差 | 描述精准，路由稳定 |
| **执行合规度** | 用了但没按流程走 | 部分步骤被跳过 | 退出条件被真正遵守 |
| **产出可用性** | 输出还要大改 | 小改可用 | 直接可用 |

**处置**：

| 总分 | 处置 |
|------|------|
| 7-8 | 保留，考虑把其中的通用部分提炼成共享技能 |
| 4-6 | 修：优先改 `description`（触发不准）或补退出条件（执行不合规） |
| 2-3 | 降级观察一个季度，仍不改善则归档 |
| 0-1 | **归档到 `skills/_archived/`**，并在 `MEMORY.md` 记一句为什么没用起来 |

**归档不是删除**。留着是为了下次别重复造同一个没用的轮子——这本身就是一条 L4 记忆。

## 六、技能的版本与变更留痕

`metadata.version` 用两段式：

| 变更 | 版本动作 |
|------|---------|
| 改错别字、补例子 | 不动版本 |
| 改流程、加减步骤、调退出条件 | 次版本 +1（`1.0` → `1.1`） |
| 改 `description`（影响路由）或 `allowed-tools`（影响权限） | **主版本 +1**，并在 `memory/` 记一条变更留痕 |

**改 `description` 和 `allowed-tools` 必须留痕**：前者改的是"什么时候会被调用"，后者改的是"能碰什么"。这两样等同于改权限，属于 `SECURITY.md` 红线 3 的范畴。

## 七、自进化的诚实边界

**能做到的**：把重复出现的做法固化成流程；把踩过的坑写成反面清单；随使用变准。

**做不到的**：

- **不能自己改 `SOUL.md` / `USER.md` / `AGENTS.md` 而不告知**——人格、用户模型、运营规则的变更必须显式告诉搭档（`SOUL.md` 模板本身就要求"改了要说"）
- **不能优化自己的权限**——`allowed-tools` 只能收窄不能自行放宽，放宽必须人工批准
- **不能替代评估**——技能变多不等于变好。没有 §五 的打分淘汰，闭环会退化成技能囤积

**想要更强的自动优化**：可以引入 `hermes-agent-self-evolution`（DSPy + GEPA，从执行轨迹优化技能文件，约 $2–10/次，无需 GPU 训练）。但那属于外挂工具链，**优化结果同样要过本文件 §三 的审批门控**。
